# 文档分段总结方法论（text-summary-filter 设计依据）

## 1. 问题：为什么分段会稀释"专注力"
长文档直接塞进上下文有两难：
- 一次性塞不下（超 token 预算）；
- 即使塞得下，模型对超长文本中段和尾段的主旨把握也会下降，等于"注意力被摊薄"。

朴素做法（切成等长碎块各自总结）更糟：每块失去全局语境，块与块之间的因果、指代、时间线全部断裂，最终摘要各说各话、重复且丢主线。我们把这种损失叫**专注力稀释**。

## 2. 四道防线
### 2.0 先问总结目标（第0步，动手前）
切分和总结都是成本动作，方向错了全白费。**拿到文档先问用户：要总结什么**（目的/用途/重点关注哪些方面），再决定怎么切、总结多深、哪些内容可取舍：
- 目标决定取舍：聊天导出、会议记录里大量寒暄/客套/闲聊，与目标无关的应在整理阶段剔除，而不是平铺总结一遍。
- 用户明确说"全面总结/你看着办"时，才按全面总结执行。
- 实战教训：某次 32 万字聊天导出未问目标直接全量总结，约 1/3 是"我在这里/祝开发顺利"式填充，等于把大半工废在无意义内容上。

### 2.1 自生专注力定块大小（先算再切）
切之前先量：字符数、句子数、平均句长、估算 token。块大小**由文档自身特征推导**，不靠外部预算硬塞：
- 块大小 = clamp(max(平均句长 × 每块期望句数, 总字符 ÷ 100), 800, 3000)。（**用户硬下限覆盖此式下限**：单块最小 40000 字符〔集中一条条文档可降到 10000〕，结构松散再乘 `--looseness` 1.2~10，上限受 `MAX_CHUNK` 与 `--context-cap` 约束；脚本 `--min-chunk`(默认40000)/`--looseness`/`--context-cap` 即对应此规则，详见 `guide/splitting.md`「按结构定块大小/重叠」。）
- **关键**：句子越碎（聊天记录平均句长才十几字），单句信息越少，越需要更多句子才能凑成一个完整意思，块应**更大**而非更小——旧公式"平均句长×句数"会把短句流切成几百个碎块（方向反了）。故加"最多约 100 块"的规模保护（总字符÷100）兜底，并把下限从 400 提到 800（此 800 为密度公式内层下限，最终仍受用户硬下限 40000 约束，见上句）。
- 句子越密（平均句短）→ 块可小；越长 → 块需大，保证每块自洽、不断章。

> `--sents-per-chunk` 控制每块期望句数（默认 12）；也可用 `--chunk-size` 手动覆盖。这样"每块都在文档舒服的区间里"，从源头避免稀释。

### 2.2 等宽切块 + 滑动重叠
- **等宽**：按推导出的块大小切成**大小相等的块**（吸附到句子边界；末块因余数可能略短；单句超块则整句成块，绝不切断行）。
- **滑动重叠**：相邻块之间，把**前一块尾部默认 1-4kb**（按文档信息密度升降档）原样重复到下一块开头。边界处的半句话、未完列举、刚提到的实体，都能被下一块看见，断章问题大幅缓解。

> 默认 1-4kb 绝对值重叠（1024~4096 字符），可按文档信息密度升降档：信息密度高（条款/列表）取小档省 token；叙事松散、指代多取大档保衔接。需钉死固定重叠量用 `--overlap-chars <字符数>`；`--overlap` 仅作手动按比例覆盖。

### 2.3 重叠标记
脚本在重叠区打 `⟦OVERLAP 来自块N尾部·重复区⟧ … ⟦OVERLAP 结束⟧` 标记。该标记有两个用途：
- 让模型明确知道"这段是上一块尾部带下来的"，属于本块内容、随块自包含；
- 供最后**统一整理**阶段定位重复/冲突，不在总结中途处理。

### 2.4 逐块隔离 + 只追加
- **隔离**：每块总结只允许读自己那一段的文本（含随块带入的 `⟦OVERLAP⟧` 重叠尾巴，属于本块内容），不引用其他块、不借助全局上下文。保证每段摘要纯粹、可被独立验证，也杜绝"用后面块内容反补前面块"的污染。
- **只追加**：每块摘要产出后直接追加进总结果，**总结过程中禁止删改、去重、裁决冲突**。好处：每块互不影响、可并行、事后统一处理简单。
- **读一次写一次（操作流程）**：绝不一次性把整篇文档读进上下文。可先通读一遍仅在心里建立全局印象（不产摘要），随后压缩上下文、逐块推进——读一块、总结一块、写一块，下一块再读再写；不允许"全文档加载→一次性吐总结"。既防长上下文稀释每块主旨，也守 token 预算。

### 2.5 统一整理（最后才去重 + 裁决）
所有块摘要收集齐后，做一次统一整理（这是唯一允许跨块综合的步骤）：
1. **去重**：因默认 1-4kb 重叠，相邻块摘要会出现相同内容，统一剔除、保留一处。
2. **合并互补**：不同块提到的互补信息合并成完整表述。
3. **冲突裁决**：若数字/结论/时间线相互矛盾，**必须问用户**——保留前 / 保留后 / 都保留 / 自定义。批量列出所有冲突项一次性问，不每块打断。

只有 100% 确定是"设计性纯重复"且无信息损失时才可自动去重；但凡有冲突或歧义，一律问。

**配套规则**：
- **无关注释**：与总结目标无关的内容（寒暄套话、客套填充、闲聊）整段剔除不占篇幅；非目标相关但可留用的观点入附注留痕。
- **分段整合**：块摘要上百条时先按块号段拆分各做分段整理，再对分段结果做元总结，避免元总结本身吞不下、丢主题。
- **结构盘点先行**：整理前先从原文提取"结构清单"——文档自称的核心子系统、功能模块、条款编号（如 aa~ct 编号体系），作为覆盖核对基线；没有显式编号的按主题聚类反推。没有这份基线，就没有"漏没漏"的判断依据。
- **子系统完整性硬标准**：原文声明的核心子系统，终稿必须各有规则级内容（可执行的参数/条件/公式/流程）；"接XX大改""详见XX"式裸引用不算覆盖——要么展开写，要么明确标注"原文即引用、无细则"。
- **分散型内容强制合并成模块**：某功能的多个碎片散落在不同块（如"录制/回放"=脏标记+24分钟全量快照+自动补救+中断回退，分散在几十块里讨论），整理时必须合并成独立功能模块条目，不允许拆散归入无关主题、更不允许在主题归类中蒸发。
- **覆盖度自评**：终稿附一句"X/Y 条有规则级落点"的覆盖度自评，让遗漏可量化、可复查。
- **冲突裁决两种模式**：交互式（默认问用户）vs 无人值守（自动取更完整版+终稿文末列"待确认冲突项"供事后裁决）。
- **中间产物先留后清**：终稿产出前各级产物不删（保追溯、可补救）；终稿就位并校验后按 2.8 清理，只留源文档+终稿；终稿格式默认 txt（md 为过程稿，交付时删）。

### 2.6 并行（需用户允许 + 并发数由 Q4 用户自定）
块间无依赖、环境也支持，但**开多个 Agent 前必须先经用户同意**；并发数由开场 Q4 用户自定，**不设上限、不钳制**；CPU 型号/规格（云端 API 分支）只用于给建议值、不看可用内存，本地模型则按 GPU/NPU 能力与急不急定思考强度。默认串行 1；重文本任务建议串行 1；未同意并行则顺序执行。429 只是云端配额的次要风险（实测 8 并发即有 worker 被打断、白跑一轮），不得当本机并发主判据。冲突裁决仍在统一整理阶段集中处理。

**并行执行纪律（实战教训）**：①先试水再铺开——派多个前先派 1 个验证模型可用、不撞 429，再按 Q4 用户设定的并发数铺开；②框架报 failed 先查文件系统再重跑——后台 Agent 可能已写完仅卡在最后合并/回传（实测 2 个"failed"worker 的文件其实都在，补一条 cat 合并即完整恢复），先 ls 看产出、缺什么补什么；③每个 Agent 认领独立区间、写独立临时文件，主 Agent 最后合并，防写冲突。

### 2.7 元总结后二次查漏（防丢主题 + 防压扁 + 防蒸发）
元总结是把 N 条块摘要压成一条全局摘要的"再压缩"步骤，而**压缩必丢信息**。终稿产出后必须做二次查漏，且必须是**双轨核对**：

- **轨道一：逐主题比对**——主题清单来自分段整理的标题结构，确认每个主题都在终稿有对应落点；
- **轨道二：按原文结构清单逐条核对**——用整理前盘点的"结构清单"（文档自称的核心子系统/功能模块/条款编号）逐条查覆盖。**主题归类法对"分散型内容"天然失效**：一个完整功能模块的碎片散落在几十块里，归不进任何显性主题，主题比对永远发现不了它——只有结构清单能兜底。

**子系统完整性硬标准**：原文声明的核心子系统，终稿必须各有**规则级落点**（可执行的参数/条件/公式/流程）；"接XX大改""详见XX"式**裸引用不算覆盖**——要么展开写，要么明确标注"原文即引用、无细则"。

**实战教训（32 万字设计文档，两次漏法各不相同）**：
- 首版元总结漏掉 4 个整主题（灵魂沙吞噬机制、方块表面与水洼、TurboWarp 电学沙盒、全生物 AI 框架）——靠轨道一补回；
- 更深的坑：原文自称的六大子系统中四个（流体/天气/农业/生理）被压成"接XX大改"一句、**录制/回放系统整块蒸发**——这类遗漏轨道一完全查不出（它不在任何分段主题里），只有轨道二的结构清单核对能防住。

**覆盖度自评**：终稿附一句"X/Y 条有规则级落点"（Y=结构清单条数），让遗漏可量化。用户完整度要求高时，双轨核对为必做步骤。

### 2.7.1 数字数据零遗漏（硬性，第三轨）
双轨核对解决"主题/模块漏没漏"，但漏不了另一类隐蔽丢失——**数字**。文字概括可以丢修饰、丢例子，数字却是规则的可执行部分：一个阈值、一条公式系数、一个时长表，漏一个数整套设定就失真甚至失效。而多级压缩（逐块总结→分段整理→元总结→二次查漏）每一级都在丢细节，数字正是最容易被"概括掉"的（如"约20秒"被概括成"很快"、"20×(1+行为+护甲+武器)"被丢成"动态伤害"）。

规则：**原文出现的所有数字数据——参数、阈值、时长、尺寸、配比、百分比、范围、公式系数、编号、版本号、坐标、层级——终稿必须一个不少**。

落地做法（第三轨核对，与前两轨并行执行）：
1. 用正则从原文抽取"数字指纹"：数字连同其单位/范围/百分比/公式上下文（如 `24分钟`、`9×9`、`0-100`、`64-96`、`万分之一`、`Y0~-16`、`20×(1+行为+护甲+武器)`）；
2. 与终稿做集合比对，列出差集（原文有、终稿无的数字）；
3. 差集逐个回原文定位、确认是实质数字还是寒暄里的数字（如"100%确定"这类语气词可豁免），实质数字补回终稿对应条目；
4. 补完才允许交付——数字核对是交付前的最后一道关。

### 2.7.2 全信息附带 + 来源标明（硬性）
数字的"零遗漏"只解决了规则可执行部分；还有一类更隐蔽的丢失——**整段内容被蒸发**。文档内陈述的设定、论点、例子、决策、风险、流程、结论，在"逐块总结→分段整理→元总结"的多级压缩里，会因"散、次要、难概括"而被悄悄丢掉的，远比数字多。

规则：**文档内可得到的全部信息，终稿都要有落点**——不擅自删减、不选择性丢弃任何文档内陈述。总结可压缩表达、可合并同类项、可剔除与目标无关的寒暄，但"文档里说的，终稿里都要找得到"。某段内容散落在几十块、归不进显性主题，也不能蒸发，必须合并成独立模块条目（见 2.5 分散型内容强制合并）。

同时**明确标明来源**，让终稿可被追溯、不被误读为创作：
1. 开头声明"本总结全部内容提炼自《原文档名》，不含文档外信息"；
2. 正文按块/章节标注出处（如每段注「块N」「第X节」）；
3. 文档外的推论/补充/点评须与原文**显式区分**（标「（AI 推论）」等），绝不与原文混写，避免以假乱真。

覆盖度自评需注明"文档内信息 X/Y 类已附，余为文档外标注"——把"漏没漏"从感觉变成可量化。

### 2.7.3 终稿交付后询问用户是否二次检查（硬性收尾）
终稿就位并校验后，**必须主动询问用户是否要做一次"二次检查"**：再对照原文逐条/逐主题核查遗漏，或针对用户指出的特定段落补查（重读原文、补数字指纹比对、补遗）。不要把交付当终点就沉默——用户可能刚发现遗漏、或想换角度复查。用户选"要"则进入二次检查流程（重跑数字指纹比对 / 针对指定块重读原文补遗），选"不要/暂缓"则正常收尾。这一问是交付闭环的最后一步，不可省略。

### 2.7.4 终稿整理只改位置、不删东西（硬性）
统一整理与交付前对整篇总结文档做"整理"时，**只能调整内容的位置**（归并、重排、把补遗/数字回填移入对应块、把结构盘点前置为目录），**绝不允许删除任何文档内信息**。可合并分散碎片成模块、把批尾的数字补遗挪到所属块、把结构清单前置为导航——但每一条原文陈述（数字/例子/决策/风险/流程）都必须保留落点，清零即违约。整理目标是"读着顺、溯源清"，不是"瘦身"。与 2.7.2 同源：丢内容是绝对红线。

### 2.8 交付与清理
- **命名与位置**：终稿 = 原文档文件名后加"总结"二字（`报告.txt` → `报告总结.txt`），与输入文档同根目录，用户找得到源也找得到果。
- **格式**：默认 txt（去 markdown 符号、保留表格），另可按需附 md。
- **清理**：终稿就位并校验（行数/大小/头部）后，删掉全部中间产物（chunks/、逐块摘要、分段输入/整理、临时批文件、过程稿），只留源文档+终稿——**先落后删，顺序不可反**；删除前在回复中列明清单供追溯。
- **落地技巧**：mv / Rename-Item 等文件系统移动可能被安全策略拦截，"读内容→写新文件"是可靠替代。

## 3. 切分边界规则
| 规则 | 做法 |
|---|---|
| 一级边界 | 空行（段落） |
| 二级边界 | 句末标点 。！？； 及换行 |
| 等宽 | 目标大小相等，按句边界吸附；末块可能略短 |
| 绝不切断行 | CJK 一律在标点/换行处断；单句超块上限则整句单独成块（宁可超，不切断） |
| 重叠吸附边界 | 重叠量按字符计，但抓取时吸附到最近的自然边界单元，保证重叠区也是整句 |

## 4. 关于重叠口径（现行 1-4kb）
用户早期原话曾提出「按参考文档大小的百分比做重叠」，该历史口径已废弃，以本版正文为准。**现行口径**：默认 1-4kb 绝对值重叠（可按文档信息密度升降档），不按百分比、不按参考文档大小；需钉死固定重叠量时用 `--overlap-chars <字符数>`。

# 踩坑与恢复速查（troubleshooting）

用法：按「现象」定位 → 看「根因」→ 直接照「修复」执行。每条均来自本轮或前期实战。
三条总原则：① 报 `failed` / 超时 / 429 / 零产出，先查文件系统再下结论；② 切分/拼接/校验一律二进制模式；③ 校验必须程序化，不靠人眼/推理。
与 `zero-loss-merge.md`、`three-pass-screening.md` 配套：本文只收「现象→根因→修复」条目与命令，不复述流程。
不确定口径标 `(待核)`，不编造。

## A·补 shell 内联 Markdown 反引号坑（本轮实测复发 3 次，硬性）

现象：用 `python -c "..."` 或 bash 双引号字符串拼装含 Markdown 反引号的中文文本，
写出的文档里反引号包围的部分整段消失（如某个 Markdown 文件名与
表格段落被打残），且不报错、退出码 0，极难当场发现。

根因：反引号在 bash 双引号内是命令替换语法，shell 会先执行反引号里的文字当命令，
把其 stdout（通常为空）替换进去，Python 拿到的字符串已经缺字。

修复（硬性）：
- 任何含反引号的中文 Markdown（表格、代码标记、文件路径），一律用 Write / Edit 工具直接写文件，
  或先 Write 成补丁文件、再用 Python 读文件拼接；绝不经 shell 字符串。
- 若必须用 bash 内联，把外层改成单引号且确保文本内无单引号，或先 `set -H` 关闭历史扩展仍不够——
  最稳妥就是不这么做。
- 写完后校验反引号数与关键文件名仍在：`grep -c "<关键路径>" <输出文件>`，
  或比较补丁文件与结果文件的字节数。
- 三次中招位置：章节首次追加、工具文档段落、日志/总表末段追加；
  均已用「Write 补丁 + 文件拼接」修复。

## A·补2 静默吞异常（`except: pass`）掩盖真缺陷（本轮实测）

现象：`run_pipeline.py init` 新增的「判定素材自动摘录」一直没生效，基准里始终是通用占位文本；
脚本不报错、退出码 0，肉眼几乎看不出。

**根因**：摘录逻辑用了 `re.match` / `re.sub` / `re.findall`，但文件**没有 `import re`**；
外层 `try: ... except Exception: pass` 把 `NameError` 静默吞掉，`excerpt` 保持空，
于是走「无摘录」分支退回默认定义。

修复（硬性）：
- 脚本级 `except` 至少打印一行警告（`[警告] … 失败：<异常>`），绝不裸 `pass`；
  确实要忽略的窄异常（如 `reconfigure` 的 `AttributeError`）要写明具体异常类型与原因。
- 新增功能后必须验证「功能真的生效」，不能只看「命令退出码 0」：
  检查产物内容（本例是基准里有没有摘录的 5 行），而不是只检查文件存在。
- `skill_selfcheck.py` 只能查语法/参数/引用，查不出这类运行时静默降级；
  所以 `smoke_test.py` 的链路冒烟（验证基准内容、提示词路径、S4 停住）是必要补充。

本轮同类：`except Exception: pass`（读取 merge_state / 摘要卡统计）也已改为打印警告或明确注释，
避免再次静默降级。

## E. 中断 / 失败恢复判定树（先查再动）

```text
agent 报 failed / 超时 / 429 / 后台零产出
  |
  +-- 1. 查文件系统：ls 输出目录、wc -l 各文件、查 agentN_result.json 是否存在
  |
  +-- 2. 判定产出状态
  |     +-- 已产出（文件完整、行数合理、JSON 合法）  -> 不重跑，直接接续下一道
  |     +-- 部分产出（缺区间 / 压缩比异常 / 半截 JSON）-> 备份半成品，只补缺失区间
  |     +-- 零产出                                    -> 前台重跑该道，加防重复写入
  |
  +-- 3. 重跑纪律
        +-- 严格串行、前台、一次只 1 个 agent
        +-- 防重复写入：写前查目标文件是否已含本道标记 / 计数是否已 +1
        +-- 不整批重跑、不覆盖已写好文件
  |
  +-- 4. 结论先行：先把「已产出/部分产出/零产出」写在回复里，再动手
```

严禁仅凭框架报错下结论。实测有「2 个 failed worker 文件其实都在」的情况。

## F. 通用工程红线速记

1. 切分 / 拼接 / 校验一律 `rb` / `wb`，或 `newline=''` + `encoding='utf-8'`；字节比对用 `b''.join`，不用文本比对。
2. 读文件先剥 BOM；行号统一 1-based 物理行号，与 `L<n>|` 严格对应。
3. 切分点严格两行之间，绝不切断行；拼接后必做 `assert joined == raw`。
4. 硬数据比对只报种类差集（`set`），不用 `Counter`；比对前规整全半角、千位逗号、版本号整体、大数字子串噪声。
5. 原文零改写：agent 只给行号 + 理由，原文由脚本按行号逐字节抽取。
6. 逐行去向映射文档放在输出文档之外单独存放；`_merge_state.json` 状态常量与所有校验脚本一致。
7. 严格串行、前台跑、一次只 1 个 agent；后台 agent 在本环境必定零产出，不再重试。
8. 每道 agent 只回一行确认，正文零回流主线程；框架报错先查文件系统。
9. 改前先备份、不主动删文件；错误版本移 `_bad/` 保留；顺序铁律「先落终稿、校验通过、再动中间产物」。
10. 校验必须程序化，人眼 / 推理不可靠；`(待核)` 项不编造、原样保留。
11. 差集回原文 Grep 定位后程序定性排除噪声（CDN 哈希 / auth_key / 13 位时间戳 / 纯章节序号 / 全半角 / 大数字子串），补漏清单为空才交付。
12. 单块上限按磁盘字节验（≤100 KB）；`--chunk-size` 是字符数，中文须 ×≈3 换算（C14）。
13. 来源标签 `[来源：]` 必须填原始稿文件名，绝不填 `chunk_xxx`；文档骨架行一律保留（D21/D22）。
14. 停止压缩双阈值（压缩比≥0.9 / 输出≥输入 / 连续 N 轮无下降）触发即停并报告「已达零丢失下限」，禁止为凑篇幅强压。

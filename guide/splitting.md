## 切分规格

### 切分规则（硬性）

- 切分程度预算先行（总结前必做）：切多细不是拍脑袋——总结前先按文档大小选档，再按预设算法（自生专注力公式）或自定义算法（`--chunk-size` / `--sents-per-chunk` / `--overlap-chars` 手动覆盖）确定切分程度，并算出切分预算：预计块数 = 总字符 ÷ 块大小，本次总成本 ≈ 块数 ×（块大小 + 重叠量）× 2（读+写）。先有预算再动手，避免切完才发现规模失控。
- 大文档切出很多块是必然且正确的：不要为减少块数而用超大块——超大块单次读取更贵、专注力更稀释，总成本反而更高、丢主旨风险更大。正确的省法是「块数多 × 每块轻 × 块内容不回流主线程」（见「省 token 硬流程」），不是「块数少 × 每块巨」。
- 每一块大小相同：目标等宽，吸附句子/段落自然边界；末块可能因余数略短；单句超块上限则整句成块（宁可超，不切断行）。
- 只切在自然边界：优先段落（空行）边界，其次句子（。！？；\n 等）边界；绝不把一个字符切成两半——CJK 文本一律在标点/换行处断。
- 边界重叠默认 1-4kb 绝对值（可按文档信息密度升降档）：后一块开头重复前一块尾部 1-4kb，吸附到自然边界；信息密度高（条款/列表）取小档省 token、松散叙述取大档保衔接。需手动按比例覆盖时用 `--overlap`（0~0.5），需钉死固定字符数用 `--overlap-chars <字符数>`。重叠区会被总结两遍，重叠越大 token 越费。
- 重叠量默认由文档体量与信息密度决定为绝对值 1-4kb（`--overlap-auto`）：≥50万字符→4096、≥10万→2048、否则 1024——文档越大/越松散边界语境越贵，取大档保衔接；密集条款式取小档。可用 `--overlap-chars` 手动升降档钉死（见下「按结构定块大小/重叠」）。
- 重叠文本用 `⟦OVERLAP 来自块N尾部·重复区⟧ … ⟦OVERLAP 结束⟧` 明确标记。

### 按结构定块大小/重叠（先看结构再定参数，信息密度算法）

切分前必须先看一遍文档结构，判定「零散宽大 / 紧凑密集 / 集中一条条」，据此定块大小与重叠，绝不无脑套默认。核心算法：按信息含量定块。

- 用户经验基准：正常 AI↔人 对话，一百字里只有 4~5 字是有用信息（有用率≈0.05）；一条条集中文档有用率可达 0.85。块大小与有用率成反比——块字符 ≈ 目标摘要字数 ÷(有用率 × 保留率)。脚本 `estimate_density()` 用「短行比 / 列表·条款密度 / 平均句长 / 平均段落」多信号融合判定 band 与有用率，顾及自生上下文、不盲信单一信号（不低估也不高估自己）。
- 块大小下限 40000 字符（≈40kb，仅「信息密度推导的下限建议」）：普通文档单块不小于此；低于 40000 一律抬到 40000。⚠️ 但本下限绝不得凌驾全局硬红线「任何时候切出的块都必须严格 < 模型上下文的 1/2」：half_cap 更小时忽略下限、块强制缩小到 < half_cap。本文件对应新流程第 1 步「切块总结」的等宽切分（⓿ 前置做切分预算与上下文容量判定）。唯一例外——集中一条条文档可降到 10000 字符（≈1万），因这类文档"总结也压缩不了多少"，硬撑 4 万只费 token。
- 紧凑 ×0.1~~1 / 松散 ×1.2~~10：结构紧凑（高密度条款/列表）→ 在 40000 基础上乘 0.1~~1（更密可更小，但受 1 万下限保护）；结构松散（宽大叙述、百字仅一字重要）→ 乘 1.2~~10 放大块（文档越散乘越大：40k×1.5≈6万、×2≈8万、×10≈40万）。`--looseness` 手动覆盖系数。
- 块至少要几万、正常几万到几十万：AI 专注度没那么低，"一次只总结几千字"太少了——少说几万字符起；很松散的文档块可到几十万字。但必须受上下文窗口约束（见下）。
- 每块总结后文本量（建议 2000~4000 字，非硬约束）：这是摘要层的建议目标长度（数字/决策/方案/关键原话全保，寒暄/重复不进），超出不强制截断。完整性永远优先于篇幅：宁可摘要偏长、块偏大，也绝不为了凑字数而砍掉设定/数字/冲突；集中一条条文档本就压缩不动，摘要偏长属已知例外（宁可块 1 万、摘要偏长，也不强行切碎）。
- 必须受上下文窗口约束（且**全局硬红线：任何时候切出的块都必须严格 < 模型上下文的 1/2**）：放大后的块不得超出读块 Agent 的上下文——单块字符数钉死在 `（上下文窗口 − 系统提示词 − 生成余量）` 之内，用 `--context-cap <该值>` 传入。运行环境不清楚上下文具体大小时，先问用户要「减去系统提示词后的可用字符/token 数」，再定 `--context-cap`；绝不允许切块超窗（超窗直接失败且浪费积分）。
- 判定速查（`--analyze` 输出辅助）：宽大松散=平均段落 >600 或长段落占比 >30%；紧凑=平均句长 <70 且列表/条款密度高；集中一条条=列表密度 ≥6 且平均句长 <120。

### 块 < 1/2 上下文硬红线与钳制逻辑（全局硬红线，代码必须真正执行）

- **适用范围**：不只第 5 步检查重切块，**第 1 步切块总结、第 6 步切块检查**同样适用；第 5 步重切块固定以「上下文 1/2」为上限（`--check-rechunk-cap`，默认取 `--context-cap/2`）。
- **块上限 = half_cap**：`--context-cap` 是上下文容量，`half_cap = context_cap // 2`，最终块大小**必须严格 < half_cap**（实现取 `half_cap - 1` 留安全余量），不再用整个 `--context-cap` 当块上限。
- **下限不得凌驾**：`--min-chunk`（默认 40000）只是信息密度推导的下限建议；当 `floor >= half_cap` 时**不得**用 floor 把块顶回，必须服从 half_cap，并打印明确告警（上下文太小、块被强制缩小、块数会变多）。
- **可观测**：钳制须打印 `ideal / floor / cap / half_cap / 最终块大小 / 钳制原因`，不静默钳死（审计 N-P1-2）。实现见 `scripts/merge_and_chunk.py` 的 `_derive_size()` 与 `scripts/split_document.py` 的 `derive_chunk_size()` / main。

### 切分算法预设（主观选型参考 · 核心原则第 16 条授权）


由文档性质主观选定预设；所有预设均继承上方硬性切分规则（等宽 / 自然边界 / 默认 1-4kb 重叠 / 绝不切断行）。预设 D 为默认兜底；选型后若文档某段出现特殊结构（如代码块），临时升级对应预设，不换全局。

- 预设 A｜等宽字符块（通用默认）：固定块 N 字符，相邻默认 1-4kb 重叠，吸附句/段边界。N 由自生专注力推导 `clamp(max(平均句长×期望句数, 总字符/100), 800, 3000)`；短句密集文档手动上调（8000–20000）。适用：无清晰层级的长文、混合稿。优点：均匀简单、重叠防边界丢失；缺点：可能切断话题。
- 预设 B｜标题/结构分章块（结构型）：识别标题/分隔符（`---`、`#`、`第X章`、`【】`、aa/ab 条款号）为块边界；单章超长再等宽细分。适用：设计文档、需导出文件、有明确章节者。优点：块内主题一致、数字归属清晰；无标题时退化为 A。
- 预设 C｜对话轮次块（聊天型）：以"用户/AI"角色切换或时间戳为边界，每 K 轮为一堆，吸附到轮次边界、不切断单条消息。适用：多轮问答式聊天日志。优点：问答不拆散、上下文完整；缺点：块大小波动。
- 预设 D｜自适应句长 + 手动上限（智能兜底，默认）：先算平均句长×期望句数得基础块大小，clamp 到 [下限, 上限]；短句文档自动放大下限防切碎。适用：所有类型兜底，特别是短句聊天。优点：兼顾均匀与防碎。
- 预设 E｜代码/技术块感知（技术型）：识别代码块（` ``` ` 包裹）、表格、长命令/配置，整块不切断；块间按等宽合并。适用：neoforge 环境搭建、含命令/配置的日志。优点：命令可复现、不被腰斩。

选型矩阵（通用）：多轮聊天日志 → C（无标题则 D）；设计文档／需导出文件 → B；含代码／配置的日志 → E；其余长文／混合稿 → D 或 A。

## 筛选与交付

> **新 7 步归属**：本文件「三道串行筛选」对应权威流程**第 2 步「条目筛选」**（按 Q8 目标筛选、事实层判定基准在筛选前生成、只剔与目标无关的闲笔、事实／要点一律保留）；「交付与清理」对应**第 4 步「终稿生成」**（渲染定稿／分卷／逐行去向映射／交付清单）。**执行顺序已按权威流程真反转：筛选(第2步)→合并(第3步)**：编排器先跑筛选链(S3~S6)、再跑条目合并(S2)，筛选行号基准统一为筛选基准稿（`init --extract`，不给则退回母本）。

### 按行内容筛选 · 三道串行校验（防误删）

本节为按行内容筛选的主线索引，五节判定基准模板、判定视图脚本骨架、JSON 协议与四条断言见 `references/three-pass-screening.md`；三道严格串行、前台执行、不启动任何其他 agent。

- 统一判定基准（三道共用唯一标准，硬性）：动手前先写定一份 `筛选_判定基准.md`，五节模板——①判定对象定义＋应保留类别清单 ②「毫无关联」唯一可剔除标准（三条须同时满足：不含任何实质信息、不能作为设计依据／素材／背景／工具链／开发流程解释、属其他项目或纯文档工程残留）③三道分工与阈值表 ④输出硬性要求（只输出行号＋理由、脚本抽原文、物理行号、每条附理由、UTF-8 JSON）⑤零丢失底线。三道必须完整读完、共用这一份基准，不许各判各的。  
  |  |  |  
  | --- | --- |
- 判定视图：由 `build_line_view.py` 二进制读母本、零改写生成，格式 `L行号| 首55字…尾20字`（`--head 55 --tail 20 --index`），让 agent 在有限上下文内通读全部行；拿不准用 Read 回查完整原文，不凭截首臆断。
- 三道阈值梯度与输入依赖（严格串行）：第 1 道 宽松初筛（母本全量，疑似无关就拎出、允许误伤，输出文档 A）；第 2 道 极宽松抢救（仅输入文档 A、不重读母本、不引入新条目，任何关联线索——间接／素材／背景／工具／灵感——一律捞出，宁可错捞不可漏，输出文档 B）；第 3 道 终审（输入 A＋B，逐条独立回查、拿不准→放回、可否决前两道，须覆盖 B 每一条并复核 A 剩余，输出文档 C）。后道只在前道输出范围内工作，输入依赖收敛，单点误判不直接造成删除。  
  |  |  |  
  | --- | --- |
- JSON 行号清单协议：每道输出 `agentN_result.json`（`{"items":[{"line":…,"reason":"…","verdict":"…"}]}`），行号为母本物理行号、与判定视图 `L<n>|` 一一对应；写入前用只读脚本交叉校验（条数、行号唯一升序无越界、reason 非空、B⊂A、两数组互斥且并集恰为 A），不通过不落盘。
- 原文零改写抽取：agent 只给 `(line, reason, verdict)`，原文由脚本按物理行号从母本 `splitlines` 逐字节抽取生成新文档，严禁手工复写／缩略／截断。
- 终局集合硬校验：四条断言全绿才交付——剔除集 ∪ 放回集 ＝ 初判全集且两者互斥、行号无越界、定稿与筛选基准稿（删剔除行后）逐字节一致、硬数据指纹零丢失。
- 剔除行内容体检（语义层护栏，硬性）：数字指纹只能查数字类硬数据，删掉一整行纯文字设计条目是查不出来的。生成定稿时必须统计「终审剔除集中含文字（字母/数字/中文）的行」，落盘到输出文档之外的 `剔除行内容体检.md`，运行报告里给 `PASS`（0 行）或 `WARN`（>0 行，须人工确认确属「毫无关联」）。`verify` 会独立补做此项，旧工作区也能补验。S7 的 note 不得再无依据地写「设计条目 0 删」。
- 「指纹零丢失」不等于「内容零丢失」（硬性认知）：三类指纹（编号/数值+单位/冲突标记）只覆盖数字类硬数据；纯文字概念、设定、机制被整行删掉时指纹仍全绿。因此零丢失必须由三条互补证据共同支撑：①数字指纹集合层 0 缺失 ②剔除行内容体检（无含文字行被删，或人工确认）③零散内容块分区核对（自动探测生效、未静默误删整片）。缺任一条都不得宣称「零丢失」。
- **短路模式 `--screening off`**：`init` 加 `--screening off` 即跳过筛选链 S3–S6，直接以筛选基准稿进入合并/分卷（合并现在在筛选之后）；S2 按空剔除集落盘、S7 出定稿、S8 分卷、S9 报告照常跑，不会停在 S4 等 agent JSON；`verify` 相应跳过三道集合与剔除行体检，只验指纹与分卷拼接。由 `route.py` 对「只合并 / 仅合并」自动给出此参数。
- 主线程额外独立抽查（必做）：第 1 道之外，主线程另独立抽查是否漏拎大块无关内容——第 2／3 道只能复核 A 内条目，第 1 道漏掉的救不回。
- 执行纪律：严格串行、前台执行（后台 agent 在本环境必被回收零产出）；被中断重跑前先查有无残留 JSON 再前台补跑；每道只回一行确认。

### 交付与清理

- 终稿命名：原文档文件名后加"总结"二字（如 `报告.txt` → `报告总结.txt`），与输入文档放同一根目录。
- 终稿格式：默认 txt（去 markdown 符号、保留表格结构）；md 仅在用户明确需要时才保留，否则作为过程稿删除。
- 中间产物先留后清：终稿产出前，各级产物（chunks/、逐块摘要、分段输入、分段整理）必须保留，供追溯与补救。顺序铁律：先落终稿、校验通过（行数/大小/头部正常），再删除全部中间产物（chunks/、逐块摘要、分段输入、分段整理、临时批文件、过程稿），只保留源文档与终稿；顺序反了等于把工果实拆了。
- 删除前先在回复中列明删了什么（目录/文件数/大小），让用户可追溯。
- 落地技巧：文件系统移动/重命名（mv / Rename-Item）可能被安全策略拦截，"读内容→写新文件"是可靠的替代方式。

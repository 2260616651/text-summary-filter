## 不可变量

### 红线禁忌（硬性，绝不可违反；各原则中标「硬性」的项在此汇总强调）

> **零丢失的定义（先读这条）**：「零丢失」= **信息 / 要点不丢失**，不是「一个字节不丢失」。红线约束的是**信息完整性**——源文档的事实、数字、决策、流程、要点在终稿中都必须可定位、可追溯，缺一条即违规。本 Skill 默认采用「按行忠实抽取（绝不切断行 / 零改写 / 逐字节可还原）」作为实现手段，因为它是保证不丢信息最稳妥的方式；但手段不是目标——只要事实与要点全部保住，**改写措辞、合并重复、丢弃与用户目标无关的闲笔都允许**。下文标「硬性」的字节/行级规则是「默认手段」的落地要求，非目标本身；若改用 AI 改写/合并等能保住全部信息的方式，同样满足红线。

以下任一条违反都会直接废掉总结质量或撑爆上下文，执行时逐条对照、不可打折扣：

1. 切分以信息单元为界（默认沿自然边界断）：切分／合并默认在标点 / 换行 / 段落自然边界断，不人为劈碎信息单元（原则 2）。这是实现「不丢信息」的默认手段；目标是不破坏信息单元的可读性与可还原性，而非「半个字不许劈」的字节约束。
2. 块内容零回流主线程：逐块总结必须「一块一 Agent、即开即毁」，块原文与块摘要正文任何时刻不进主线程上下文，只回一行确认。违反即撑爆上下文、废掉省 token 设计（原则 3 / 省 token 硬流程）。
3. 数字一个不许丢（原则 7）：参数 / 阈值 / 百分比 / 坐标 / 编号 / 公式系数等全部保留，丢一个设定就失真甚至失效。
4. 不删任何文档内信息（原则 8/11）：可压缩表达、可合并，但原文陈述终稿必须有落点；整理只改位置、绝不删内容。
5. 来源必须标明（原则 8）：开头声明提炼自何文档，按块 / 章节注出处；文档外推论显式标「（AI 推论）」，绝不与原文档混写。
6. 默认串行 1；并发数由 Q4 用户自定，**不设上限、不钳制**；CPU 档位只给建议值，开多个 agent 必先经用户允许（原则 3）。本机并发建议按 **CPU 档位**估、不看可用内存；429 只是云端配额的次要风险（用户要等约 2 小时，实测 8 并发即打爆模型配额），不得当本机主判据。
7. 总结前先去重（流程 3）：整篇级三档去重未跑完不得切块，否则 Agent 总结两遍一样的话。
8. 默认 1-4kb 重叠（可按文档信息密度升降档）、由文档体量与密度定（`--overlap-auto`）：不按比例瞎给。
9. 块大小下限 40000（集中一条条文档可降到 1 万）、受上下文约束：低于下限或超上下文都禁止。
10. 自查形态 = 真读原文查内容遗漏（原则 5）：不是程序扫数字；查前先问用户查几遍。
11. 缩略档仅作参考、禁止当作合成依据（硬性）：doc-extract-filter 产出的分组摘要/缩略档（如 `group_XX.md`、v4 缩略档）只用于溯源与参考，绝不允许拿它当原文去合成、合并或二次总结——综合必须锚定原始母本；终稿/批次稿里引用的任何数字、设定、标记必须能从原始母本 grep 追到，杜绝凭浓缩档编造或脑补（实战教训：曾误称总总结"直接读原文合并"，实则综合于缩略档，经 grep 自证才平息）。
12. 动手前先问用户：这篇文档要总结什么（目的/用途/重点关注面）。总结目标决定深度、侧重点和取舍——不问清楚就对全文平铺直叙，极易把工废在寒暄套话、客套填充、与目标无关的大段闲聊上。用户明确说"全面总结"或"你看着办"时，才按全面总结执行。
13. 分析阶段（自生专注力定块大小）：先测文档体量（字符数、句子数、平均句长、估算 token），由文档自身的句长分布 + 总规模推导块大小。关键认知：句子越碎（如聊天记录，平均句长才十几字），单句信息越少，越需要更多句子才能凑成一个完整意思，块应更大而非更小——旧公式"平均句长×句数"会把短句流切成几百个碎块（方向反了）。现推导：先算密度推导值 `max(平均句长×期望句数, 总字符÷100)`，配"最多约 100 块"的规模保护防过碎。块大小是文档内生的，不靠外部预算硬塞。用户硬下限：一个文档块最少 40kb（≈40000 中文字符），低于此一律抬到 40000；结构松散时在此基础上乘 1.2~10 放大块（见「按结构定块大小/重叠」），放大后仍受上下文窗口约束（见 `--context-cap`）。
14. 切分阶段（等宽 + 重叠）：按推导出的块大小切成大小相等的块（吸附自然边界、绝不切断行）；相邻块之间把前一块尾部默认 1-4kb（按文档信息密度升降档）重复到下一块开头，让边界语境滑过去。细则见「切分规则」。
15. 逐块总结（只看这一段、只追加）：每块总结只允许读这一块自己的文本（含自带 `⟦OVERLAP⟧` 重叠尾巴），不依赖其他块/全局上下文；摘要产出后只追加，过程中不删不改、不处理重复与冲突。并行时一块一 Agent、即开即毁、块内容不回流主线程，默认串行 1；并发数由 Q4 用户自定、不设上限，CPU 档位只给建议值，且必须先经用户允许。细则见「并行总结与上下文隔离」。
16. 统一整理（最后才去重/裁决）：所有块摘要齐了，做一次统一整理——去掉因重叠产生的重复、合并互补信息；对真正的冲突（数字/结论/时间线打架）问用户保留前/保留后/都保留/自定义（批量问，减少打扰）。细则见「追加与统一整理」。
17. 元总结后二次查漏 + 自查多轮：终稿产出后，拿它对照分段整理结果逐主题比对，确认每个主题都进了终稿——分段时漏掉的主题不会自己冒出来。实战教训：首次元总结漏掉 4 个整主题（灵魂沙吞噬机制/方块表面与水洼/TurboWarp电学沙盒/全生物AI框架），全靠二次查漏补回。完整度要求高的场景这是必做步骤。
    - 「自查 N 次」的正确形态：指派 N 批 Agent 真读原文、对照终稿、边读边查内容遗漏（设定/数字/决策/流程是否被压扁或蒸发），不是用程序扫数字——程序扫只算数字核验（原则 7），查不出语义层遗漏。自查前必须先问用户具体查几遍，再据此派批。
    - 低成本自查协作：建议先让其他 AI 工具对终稿做一次自查（不消耗本会话 token），把缺失点贴回；我方再查一轮补入。即「外部 AI 端查 1 次 + 我方查 1 次」双保险；用户贴回的缺失由我方核实后补入终稿。
18. 覆盖完整性核查（防压扁 + 防蒸发）：元总结按主题归类有两个系统性坑——①原文的核心子系统被压成"接XX大改"式裸引用，规则层（参数/条件/公式）整层丢失；②完整功能模块因内容分散在几十块里、归不进任何显性主题而整体蒸发。对策：整理前先盘点原文结构清单（文档自称的子系统/功能模块/条款编号，如 aa~ct）作核对基线；终稿里每个核心子系统必须有规则级落点（可执行的参数/条件/公式/流程），"接XX大改""详见XX"式裸引用不算覆盖——要么展开写，要么明确标注"原文即引用、无细则"；分散碎片强制合并成独立功能模块条目，不允许拆散归入无关主题、更不允许在主题归类中蒸发（这类整模块蒸发逐主题比对查不出——它不在任何分段主题里，只有结构清单逐条核对能防住）。终稿附覆盖度自评："结构清单 X/Y 条有规则级落点"，让遗漏可量化、可复查。实战教训：32 万字设计文档六大子系统中四个（流体/天气/农业/生理）被压成一句话、录制/回放系统整块蒸发。
19. 数字数据零遗漏（硬性）：原文出现的所有数字数据——参数、阈值、时长、尺寸、配比、百分比、范围、公式系数、编号、版本号、坐标、层级——总结时一个都不许丢。压缩可以丢修饰、丢例子、丢寒暄，唯独数字是规则的"可执行部分"：丢一个数，整套设定就失真甚至失效。核对方法：正则从原文抽取全部"数字指纹"（数字＋单位/范围上下文），与终稿做集合比对，差集逐个补回，补完才允许交付。口径注意：区分种类覆盖 vs 计数覆盖——原文重复出现的同一数字，终稿合并同类项不算漏，只有种类缺失才是真漏；残余未覆盖需程序定性排除噪声（图片 CDN 哈希、auth_key、13 位时间戳、纯章节序号不承载内容，不算漏）。比对前先规整全角/半角字符（如全角 `％`→ASCII `%`、全角数字→半角），否则正则指纹会因编码差异漏检真假阳性。\**
20. 全信息附带 + 来源标明（硬性）：终稿须附带文档内可得到的全部信息——不擅自删减、不选择性丢弃任何文档内陈述（设定、论点、例子、决策、风险、数字、流程、结论）。总结可压缩表达、可合并同类项、可剔除与目标无关的寒暄，但"文档里说的，终稿里都要有落点"；不能因为某段内容散、次要、或难概括就悄悄蒸发。同时明确标明来源：①开头声明"本总结全部内容提炼自《原文档名》，不含文档外信息"；②按块/章节标注出处（如每段注「块N」「第X节」）；③文档外的推论/补充/点评须与原文显式区分（标「（AI 推论）」等），绝不与原文混写。
21. 读一次写一次（硬性操作流程）：绝不一次性把整篇文档读进上下文。可先通读一遍只在心里建立全局印象（不产摘要、不占总结预算），随后压缩上下文、逐块推进——读一块、总结一块、写一块，下一块再读再写；绝不允许"全文档加载→一次性吐总结"。这样每块总结都基于本块文本而非被超长上下文稀释，也守住 token 预算。与第 3 条逐块隔离、「省 token 硬流程」配套执行。
22. 终稿交付后必须询问用户是否二次检查（硬性收尾）：终稿就位并校验后，主动询问用户是否要做一次"二次检查"——即再对照原文逐条/逐主题核查遗漏，或针对用户指出的特定段落补查（重读原文、补数字指纹比对、补遗）。不要把交付当终点就沉默；用户可能刚发现遗漏、或想换角度复查。用户选"要"则进入二次检查流程，选"不要/暂缓"则正常收尾。这一问是交付闭环的最后一步，不可省略。
23. 终稿整理只改位置、不删东西（硬性）：统一整理与交付前对整篇总结文档做"整理"时，只能调整内容的位置（归并、重排、把补遗/数字回填移入对应块、把结构盘点前置为目录），绝不允许删除任何文档内信息——每一条原文陈述（数字/例子/决策/风险/流程）都必须保留落点。整理目标是"读着顺、溯源清"，不是"瘦身"。与第 8 条同源：丢内容是绝对红线。
24. 睡觉／离场／无人值守期间**允许开 agent，但必须强锁 1 个 agent 串行**（硬性）：**不是不能开 agent**，而是并发硬锁 1、同时只跑一个前台 agent、跑完再起下一个，不由 Q4 或临时判断放宽；后台 agent 仍一律禁用（会被回收零产出）。措辞是「允许但强锁」，绝不写成「禁止开 agent」。与第 6 条「并发数由 Q4 自定」不冲突：无人值守/离场场景以本条强锁 1 为准。
25. **任何时候切出来的块都必须严格小于模型上下文的 1/2**（全局硬红线，硬性，代码必须真正执行）：不只第 5 步检查重切块，第 1 步切块总结、第 6 步切块检查同样适用；第 5 步重切块固定用上下文 1/2 为上限。`--min-chunk`（默认 40000）只是「信息密度推导的下限建议」，当它 >= half_cap 时不得把块顶回去、必须服从 half_cap 并打印明确告警（上下文太小、块被强制缩小、块数会变多）；钳制须打印 ideal / floor / cap / half_cap / 最终块大小 / 钳制原因，别静默钳死（见 `guide/splitting.md`）。

#### 追加红线（零丢失合并实战沉淀 2026-11 · 编号 11~18）

以下 8 条为 2026-11 新增红线。上文 B 版既有的「11. 缩略档仅作参考」一条保留不动，两组编号体系独立并存；已有 1~10 条的编号与文字一律未改。

1. 二进制模式读写、警惕 Windows CRLF 陷阱（硬性）：切分／拼接／字节一致校验一律用二进制模式（`rb` 读、`wb` 写、`splitlines(keepends=True)` ＋ `b''.join`），或显式 `newline=''`；文本模式会把 `\r\n` 翻译成 `\n`，造成假字节差、拼接无法逐字节还原；读文件先剥离 UTF-8 BOM。
2. 忠实保留原文信息（默认零改写）：合并／筛选默认「整行原样保留或整行丢弃」，绝不改写、重写、缩略、截断任何一个字；agent 只输出「行号 ＋ 理由」，原文由脚本按物理行号从母本逐字节抽取——这是默认保真手段。允许在【信息不漏】前提下改写措辞、合并同类项；改写后须保证事实／数字／要点全部可定位。
3. 切分点默认落在两行之间、拼接默认逐字节可还原（默认手段）：按行切分时切点默认在 `lines[i]` 与 `lines[i+1]` 之间；拼接后默认 `assert joined == raw` 逐字节相等（这是默认忠实手段，便于审计）。若采用改写／合并式压缩，则以「信息可定位」为达标判据。
4. 行映射文档必须在输出文档之外单独存放（硬性）：逐行去向映射（输入 L → 输出 L，多行对一行都指向同一输出行，连续删除合并为区间并注明原因）单独成文件，绝不混进输出文档，否则既污染内容又无法校验。
5. 三道筛选共用同一份「统一判定基准」（硬性）：三道 agent 必须用同一份五节模板判定基准，不许各判各的；每道只做自己那一道，输出 UTF-8 JSON 行号清单。
6. 文档骨架一律保留、边界模糊一律不剔（硬性）：章节标题、`###` 小标题、`【…】` 分组标记、`- ` 起始符、来源标注、分隔区块等骨架即便信息量低也保留；一行只要夹带任何实质信息就整行留，不拆行。
7. 拿不准 → 放回（硬性）：终审与任何筛选环节遇到边界模糊、无法确证「毫无关联」的条目，一律放回保留，宁可错留不可误删；终审可否决前两道。
8. 已达零丢失下限必须停止压缩并向用户报告（硬性）：压缩比 ≥0.9 或输出 ≥ 输入、且连续数轮无下降即判定已达不可压缩下限，须停止并明确报告「不丢独有硬数据下不可再压、继续压必然丢设定或数字」，禁止为凑篇幅强压。

### 追加与统一整理（关键约束）

- 总结过程只追加（原则 3）：每块摘要产出后直接追加进总结果，禁止中途删改、去重或裁决冲突——保证每块摘要纯粹、互不影响，也方便并行和事后统一处理。
- 统一整理在最后（原则 4），所有块摘要收集完后一次性做三件事：
  1. 去重（二分判断，硬性）：因块间重叠，相邻块摘要会出现相同内容，但是否真重复要看它的描述：
     - 完全重复（同一事实、同口径、无新增信息）→ 删除冗余文本、指回前文（"同上 / 见 X 节"），不重写；
     - 大致重复（互补或重叠但各自携带不同信息、不同角度）→ 不许删任何一个，全部保留（即便文字相近，信息并不冗余）。
     - 拿不准一律按"大致重复"留全，宁滥勿删。
  2. 合并互补：不同块提到的互补信息合并成完整表述。
  3. 冲突裁决：数字/结论/时间线相互矛盾时，问用户保留前/后/都/自定义，批量列所有冲突项一次问完，不每块打断。只有 100% 确定是"设计性纯重复"且无信息损失时可自动去重；但凡有冲突或歧义，一律问。
- 冲突裁决两种模式：①交互式（默认）——问用户；②无人值守（如定时任务）——自动取信息更完整/更具体的一版，并在终稿文末列"待确认冲突项"（冲突点+两种说法）供用户事后裁决，不阻塞流程。
- 多批次合成的编号化 conflict registry（实战沉淀）：当综合跨多个批次（如 batch1~5）进行时，给每个冲突持久编号（早期用 `并存1~N`，后续用 `J1~N`），并在每个批次内标注；跨批次合并去重（如 `J3≡J5`、`J4≡J10`、`J1≡J18`、`并存3≡J11` 视为同一冲突只留一条，并在另一处标"已并入 X 不单列"），终稿汇总成一份「冲突总 registry」列出所有独立口径 + 已并入的演进留痕，交用户统一裁决。大致重复不删、并存标记全部保留，永不自动丢弃冲突。
- 无关注释：与总结目标无关的内容（寒暄套话、客套填充、闲聊）在整理阶段整段剔除，不占篇幅；非目标相关但可留用的观点可入附注留痕（如开发工作流建议）。

### 并行总结与上下文隔离

- 隔离（硬要求）：每块总结只接收自身文本，不共享历史、不引用其他块、不借助全局记忆。重叠尾巴随块带入，属本块内容。
- 一块一 Agent，即开即毁：总结一个块就单独开一个 Agent——它自己读块文本、自己把块摘要写盘，完成后即销毁。块原文内容绝不回流主线程上下文：主线程只接收 Agent 的输出（一行确认 / 摘要文件路径），不搬运、不复述、不粘贴块内容——块原文的 token 只消耗在子 Agent 内部，主记忆只承载轻量结果。主线程只负责：切块 → 派发 → 收确认 → 合并时让合并 Agent 自己去读盘上摘要。
- 并行（需用户允许 + 并发数由 Q4 用户自定）：块间无依赖、环境支持，但开多个 Agent 前必须先征得用户同意；并发数不设上限、不钳制，CPU 档位只给建议值；未同意则顺序逐块。重文本任务（输入 >100KB、逐行判定、大量输出）建议串行 1。本机并发建议按 CPU 档位估、不看可用内存；429 只是云端配额的次要风险（一旦触发用户要等约 2 小时，实测 8 并发即打爆模型配额），不得当本机主判据。
- 一个 Agent 总结多少段由用户自定，但建议保证 4~~24 个 Agent 能总结完：大文档切成很多块后，把若干连续块归给一个 Agent 连续总结（块内容仍不回流主线程、各自写盘）。分组粒度用户自选；推荐使总 Agent 数落在 4~~24——太少则单 Agent 读量过大易超上下文、太多则调度与 429 风险上升。单 Agent 实际读取量 = 其负责块数 ×（块大小+重叠），必须 ≤ 该 Agent 可用上下文（见 `--context-cap` 与「按结构定块大小/重叠」）。
- 并行执行纪律（实战教训）：①先试水再铺开——派多个 Agent 前先派 1 个验证模型可用、不撞 429，再按 Q4 用户设定的并发数铺开，避免整批白跑；②框架报 failed 先查文件系统再重跑——Agent 可能已写完文件仅卡在最后合并/回传，先 ls 看产出、缺什么补什么，别急着重跑浪费积分；③每个 Agent 认领独立区间、写独立文件，最后由主 Agent 合并，防写冲突；④给 Agent 发布命令时，把相关 Skill 文档地址（如 `guide/red-lines.md`、`guide/screening-delivery.md`、`references/zero-loss-merge.md`、`references/markup-protocol.md`、`scripts/*.py` 路径等）一并给到，让 Agent 严格按既定规则/模板执行，不凭空发挥、不自行改口径。

### 省 token 硬流程（成本控制）

逐条照做；与原则 9「读一次写一次」、「并行总结与上下文隔离」节配套生效：

1. 源文不进主线程：主线程绝不整读大文档。切块交给 `scripts/split_document.py`（脚本落盘块文件），主线程只读 chunks.json 里的 manifest（块号/字符数/路径）。
2. 块内容零回流：逐块总结 Agent 自己读块文件、自己把摘要写盘、只回一行确认；合并也派 Agent 从盘上读摘要。块原文与块摘要的正文任何时刻都不进主线程上下文（组织方式详见「并行总结与上下文隔离」）。
3. Agent 提示词写死「只回一行确认」：不写这句，Agent 可能把摘要全文回给主线程，撑爆上下文（实测触发 400 prompt too long）。
4. 派发最小信息：给每个 Agent 的提示词只含「它那一块的路径 + 输出路径 + 格式要求」，不带全文背景、不带其他块信息、不复述块内容。
5. 先去重再总结：整篇级三档去重在切块前用程序跑完，别让 Agent 总结两遍一样的话——A 绝对重复（md5 指纹，自动剔除，保留首次出现）、B 高度重复（相似度 ≥0.80 + LSH 倒排索引出候选簇，Agent 审核保留信息量最大的一条）、C 句级冗余（剔捧哏套话）；块间重叠区留到合并阶段统一去重。
6. 块摘要按终稿需要控制详细度：数字/决策/方案/关键原话全保，寒暄/重复/客套不进摘要。摘要层是唯一的压缩机会——摘要过长会让合并阶段 token 成倍放大。
7. 能程序跑的不开 Agent：数字指纹比对、结构完整性检查、覆盖率统计、去重候选簇生成、补漏清单生成，全部脚本化（python 正则/集合比对/difflib）；模型只花在必须理解语义的环节（总结、审核歧义簇、合并裁决）。
8. 检查阶段 Grep 定位、不通读：二次检查/补漏/核对用关键词 Grep 锁定原文位置再读局部，绝不为了找一处内容整读几 MB 文档。
9. 块数极多先分段整合：块摘要上百条时，按块号段拆 2~3 段各做一次分段整理，再对分段结果做元总结——一次吞咽过量文本是 token 与丢主题双输。
10. 中间产物落盘复用：块摘要/去重报告/补漏清单落盘后，后续合并、查漏、补漏环节一律读盘复用，绝不重复总结同一内容。
11. 同一会话保持任务连续：上下文缓存的命中依赖会话连续性——中途穿插无关长对话会作废缓存，后续每轮都按新算计费。

## 当前实现边界（实测确认，禁止对外宣称已具备）

本节只做如实的**未实现／已知限制**标注。第一批改造（统一行号基准 + 执行顺序真反转）、第二批改造（第 3 步条目合并的真语义合并）已落地；下列口径二选一或语义实现待补，如实标注。

- **第 1 步总提取稿已接入主链（已解决）**：`build_extract.py --finalize` 产出的总提取稿经 `init --extract` 入链，作为统一**筛选基准稿**（`f["screen_base"]`），筛选链视图/回查/渲染/校验/删行/指纹基线全以此为准；不给 `--extract` 则退回母本并打印告警。逐块总结本身仍属前置链（不在编排器 S1–S9 内），交付物仍不是「一份合并后的总结」。
- **删行的「零丢失」证据不覆盖纯文字（已知限制）**：新链 S2 按终审剔除行整行删除（`--legacy-merge` 时才额外机械删行）；现有「零丢失」证据只覆盖硬数据指纹集合层，**不覆盖纯文字概念／设计依据**。S7 已对 S2 删除行做「剔除行内容体检」，但含文字行仍需人工确认，因此「零丢失」只能按信息／要点口径理解，**不得宣称内容零丢失已被程序证明**。
- **「统一整理／全局摘要／去重／冲突裁决闭环」未实现**：前置链只有 `check/template/append`，总提取稿是**未去重的逐块追加稿**，没有去重、合并互补、冲突裁决或全局摘要。
- **开场询问包约 9 类参数仅记录、不改变行为（已知限制）**：`--goal` / `--final-format` / `--dedup-policy` / `--conflict-policy` / `--keep-source-mark` / `--delivery-list` / `--zero-loss` / `--mode` / `--execution` 目前**仅记录进 state，不改变行为**；`--parallel` / `--think-depth` 不作用于 ③ 逐块总结。开场问它们仍属必问（用户明确要求所有问题都必须问、问完不许再问），但须标注「当前仅记录」。
- **`--big-steps` 勾选项与状态机不是一一对应（已知限制）**：新 7 步里「第 1 步切块总结」的逐块总结属前置链、在编排器 S1-S9 里只有 S1 指纹基线作挂载点；「第 7 步达标判定与复压」为空映射（跨轮复压由 cmd_run/_reset_for_recompress 实现）；其余按 BIG_STAGE_MAP 职责归属映射，非一一对应。
- **判定基准口径固定（已知限制）**：`render_criterion` 固定为「项目设计条目」口径，未消费 Q8 `--goal`；主题混杂文档会退化。

- **编排器执行顺序与权威流程相反（已解决）**：**执行顺序已按权威流程真反转：筛选(第2步)→合并(第3步)**。STAGES 真实执行顺序 = S1(指纹) → S3/S4/S5/S6(筛选链) → S2(条目合并，吃筛选结果落盘) → S7(终稿) → S8(分卷) → S9(报告)；`run_auto` 靠列表顺序执行，重排列表即真反转。三道筛选的行号基准统一为 `f["screen_base"]`（第 1 步总提取稿或退回母本），不再锚 `f["merged"]`。
- **第 3 步条目合并的语义合并（已实现 · 第二批）**：`--semantic-merge on`（默认）时 S2 真流程＝① `scripts/merge_semantic.py prepare` 用 `difflib.SequenceMatcher` + 词元集合 Jaccard + 共享硬数据信号**机械生成**「语义相近／同类事物」候选簇与完整 agent 提示词（只产候选、不裁决，脚本不调模型）→ ② 主线程只派 **1 个前台 agent**（强锁 1、并发 1、跑完再起下一个、不启动其他 agent）裁决，产出 `合并结果.json`（每个原始物理行号恰好被覆盖一次）→ ③ `scripts/merge_semantic.py verify` 硬校验：全覆盖／无重复引用／行号合法升序／reason 非空／数字·编号·单位指纹零丢失／不得凭空新增硬数据 → ④ `render` 通过后才把合并稿写入 `f["merged"]` 供 S7 出终稿。硬红线：数字/编号/阈值/百分比/单位/范围/公式系数/版本号/配比一个不许漏、同字段多值冲突全部保留并标 `【冲突：源稿矛盾】`、文档外推论标「（AI 推论）」、不取一丢一、严格只追加语义。`--semantic-merge off` 退回第一批直通（零改写，兼容）；`--legacy-merge` 走机械删行/去重。**已知限制**：提示词由 agent 自读落盘稿全文，超大文档未按行号分片派发（判定视图分片兜底仍待实现）；纯文字概念的「凭空新增」无法机械判定，只对硬数据做正反双向种类硬校验，文字层靠提示词约束。
- **判定视图分片兜底（待实现）**：超大文档的判定视图若超出单个 agent 上下文，需按行号把视图分片派发并回收结果；尚未实现，仍是一次生成整份 `筛选_判定视图.txt`。
